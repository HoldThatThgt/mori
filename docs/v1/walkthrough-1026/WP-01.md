# WP-01 首次设置后进主窗口 检查记录

依据：2026-10-26 负责人走查（[本轮记录](../walkthrough-1026-checks.md)）第 M2 条，原话
“after setup initial model the program didn't jump to main page”；诊断与计划在会话 scratchpad 的 `diag1.json`（M2）
与 `plan1.json`（WP-01、冲突第 2、3、16 条）。在 `wt/wp01-first-run-handover` 分支上做（从本地 `app-v0` 的 63cf4a9 切出），
不推送。界面只改渲染进程，发给模型的文字、工具、批准、会话的命令和事件都没变（不是 model-facing）。

## 改了什么、为什么

负责人的问题：设置好第一个模型、测试连接成功之后，Mori 仍停在首次设置页，要在表单下方（1200×800 的窗口里多半在折叠线以下）
找到“Open folder…”再点一次。安装版的数据显示负责人在探针结束后约一分钟才点到它（诊断 M2；之后还要点“Allow public for this
project”，那一步由 WP-05 去掉网络区域时解决）。原来的行为符合当时的规格，所以这是改规格，不是修 bug。

现在：

| 情形 | 之前 | 现在 |
| --- | --- | --- |
| 测试连接成功 | 停在表单上：结果文字、表单下方测试的那个模型的探针状态、“Open folder…” | 首次启动结束（`firstRun` 置为假），进入三栏布局；中栏是 v0 的 Open a folder 提示，标题下面一行测试结果 “Connected · First token …”（成功的颜色，`data-testid="connected"`），说明 “Choose a project folder to start a session.” 和 “Open folder…” |
| “Connected · …”一行 | — | 只显示一次：有会话放进中栏（新建、打开已有的、分屏打开，打开失败的也算）时清掉，这次运行里不再出现；不跨重启 |
| 探针 | 表单下方 “Verifying tool calling…” / “Tool calling verified” / “Tool calling failed verification: …” / “Couldn’t verify: …” 与 “Verify again” | 后台照样跑（表单关闭不停止）；首次启动里不显示。打开文件夹后看会话的拒绝启动卡：验证中 “Verifying <provider>/<model>…”，探针结束自动解除；判定失败或出错时 “This session can’t start: no model fits.”，候选一行写原因，按钮 Verify now（只对还没验证的）、Change model…、Open settings |
| 测试失败、已取消、保存失败 | 表单留着 | 不变 |
| 测试失败后改了再测 | 同一张表单整体替换 | 不变（只有测试没成功时还在表单上） |

- `state/actions.ts`：`loadConfig` 的注释。
- `styles/models-settings.css`：删掉 `.first-run-open`、`.probe-status`。
- 删掉的界面文字：首次启动的 “Verifying tool calling…”、“Tool calling verified”、“Tool calling failed verification: …”、
  “Couldn’t verify: …”、“Verify again”（设置 → Models 模型行的 “Couldn’t verify: …” 照旧）；删掉的测试标识：表单里的
  `probe-status`、`open-folder`。主窗口的 `data-testid="open-folder"` 保留（WP-06 另加 `nav-open-folder`，冲突第 16 条）。

文档（先于测试与实现改）：`docs/v1/screens/first-run.md`（状态表“测试失败”“测试已取消”“测试成功”“再次保存同一张表单”、

## 按推荐替负责人定下的

负责人没单独回答 M2，诊断的推荐选项照用（本轮记录“按推荐定下的”第一条）。具体到这次实现：

1. 测试连接成功就进主窗口，不等探针，也不等 tool calling 验证通过（推荐选项；另两个选项“等验证通过再进”“留在表单上、把 Open folder…
   滚进视野”不用）。
2. 测试结果带到主窗口：“Connected · …”放在 Open a folder 标题下面、说明上面，成功的颜色，读屏 `role="status"`（临时，走查时可以改；
   first-run.md “本表定下的界面细节”）。
3. “只显示一次”按“有会话放进中栏就清掉”实现（`addTab`），包括打开侧栏里已有的会话、分屏打开和打开失败；只在界面状态里，不跨重启。
4. 探针进度只放在会话的拒绝启动卡上（诊断的推荐；M7 要删设置页模型行上的探针结果，WP-02 再加一行状态）。首次启动不再有 Verify again，
   探针出错时用卡上的 Verify now。
5. Claude 桌面版没有对应的首次设置页可照（诊断的 gap：Claude 的首次启动写法没查到对照），沿用 v0 已定的 “Open a folder”、
   “Choose a project folder to start a session.”、“Open folder…”；“Connected · …”的写法本来就取自 Claude 的 “Connected · {latency}ms”。
6. 冲突第 2 条：WP-02 要在模型行复用 “Tool calling failed verification: …”、“Couldn’t verify: …”。这次只把它们从首次启动删掉，
   `ui-strings.md` 的“探针状态”一行写明已删；WP-02 加模型行时在“设置”一节写上它们。
7. 测试的改法（不改合成端点，用它已有的行为）：
   - `tests/ui/page.mjs`：`firstRun()` 成功时读主窗口的 `connected`、失败时读表单的 `form-message`（新的 `testResult`）；
     `waitProbes(timeout, ref)` 经进程桥读 `models.get` 的档案（新的 `readProbe`、`probeState`，取值同原来的 `data-state`：
     verifying / verified / failed / error），不再读页面；手填的模型在点 Test connection 之前读。`m6-helpers.mjs`、`m2-app.mjs`
     随它改注释与输出；`m0-smoke.mjs`、`m1-app.mjs` 成功的那次测试改读 `testResult`，另查表单关掉、进入主窗口。
   - `md-app-firstrun.mjs`：要留在表单上接着测的保存（内存里的 key 与 origin、再次保存、A20 的“有改动”）都让测试失败：
     用 Add a model ID 手填 `fake-coder-404`（合成端点对它不是探针的请求回 404）；`listedRetest` 删掉（“没改动时不保存”由
     changes 的 `changesRefetch`、`changesKeptKey` 查）；新加一步 `shapes`（空列表、截断、藏起来的勾选行，最后测试成功进入主窗口）；
     nolist 的结尾改为测试取消后改勾选再测、tool calling 判定失败的拒绝启动卡（列表错误下手填完成首次启动、收到回复的那条由
     rejected 查）；rejected 的探针出错改为看拒绝启动卡上的 “tool calling not verified yet” 与 Verify now；listed 与 nolist
     两个端点每个对话请求先等 1.5 秒（原来 0.4 秒），打开文件夹时探针还在跑，看得到 “Verifying …” 卡；新加的检查查主窗口的
     Open a folder 提示（标题、紧跟的 Connected 一行、说明、Open folder…）、打开会话后 Connected 一行不再出现。
   - `md-firstrun-helpers.mjs`：表单读取去掉探针状态与 Open folder…；新加 `readMain`、`watchCards`、`watchedCards`；
     `waitTestResult` 认出“表单关掉、进入主窗口”；`waitProbe(page, ref, want)` 经进程桥；`openFolderFromForm` 改名

   - `v1-models-app-settings.mjs`（MP-33）：Local 一步另查进入主窗口与打开会话后 Connected 一行不在；Public 一步先手填

## 集成阶段要跑的

都在 `app/` 下、开发构建上，一次一个包（端口固定）：

1. `npx electron-vite build`。
2. `node tests/ui/md-app-firstrun.mjs`：MD-11、MD-08、MD-07 的首次启动检查改写最多的套件（七步全跑，不用 `--only`，否则写的是部分结果文件）。
3. `node tests/ui/v1-models-existing.mjs --id MD-15`：`page.mjs` 的 `firstRun`、`setupFirstRun`、`waitProbes` 是 m0-smoke、
   m1–m6 的 App 套件与 v1-models-app-settings（MP-33 改写、新加 `firstRunToolFailure`）共用的；这一组同时跑回放、单元、
   `spec-coverage --spec model / taskboard / memory` 与标记检查，写 MP-37、TB-46、MEM-35、MD-15 的结果文件。
   v1-models-app-settings 在这一组里，不用另跑；要先单独看它时用 `node tests/ui/v1-models-app-settings.mjs`（同样不要 `--only`）。
4. `node tests/spec-coverage.mjs --spec discovery --allow-missing-real`：MD-11 在 md-app-firstrun 与 MD-15 的结果文件都写好之后。

不需要的层与理由：

- 录 fixture：不需要。只改界面与测试，发给模型的文字、工具、批准、会话的命令和事件都没变；回放 fixture 里没有首次启动
  （回放桥的 `config.get` 给的 `firstRun` 为假）。
- 真实模型走查：不需要（同上，测试分层第 5 条）。`md-real`、`v1-models-real`、`m1-real` 里首次启动的帮助函数随这次改了，
  下次跑真实层时一并验证。
- 打包程序：没改打包配置、主进程和 preload，不在打包程序上跑相关套件；但打包冒烟用的 `m0-smoke.mjs` 首次启动那一步改写了，
  推送前的打包冒烟（`npm run dist:dir` 后 `node tests/ui/m0-smoke.mjs --exe <Mori.exe>`，再加一个 App 套件，建议
  `node tests/ui/md-app-firstrun.mjs --exe <Mori.exe>`）要用这一版的 m0-smoke 跑一次。
