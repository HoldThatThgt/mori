## 审查之后的修改（2026-10-26）

审查发现 1 个阻断、6 个次要问题，修改如下；另修了审查没提、同一类的一处。

1. 阻断：`page.mjs` 的 `readProbe`、`probeState`、`waitProbes` 只看 `models.get` 里存着的档案，而重新探测期间
   `models.get` 给的仍是旧档案（`modelProfiles.ts` 的 `profileView` 有档案就给档案，`info()` 不带 running）。m1-app 与
   m0-smoke 先用错的 key 保存（同一个地址与模型，合成端点在延迟之前就回 401，探针马上结束、存下 status 为 error 的档案），
   再用对的 key 保存时重新探测，`waitProbes()` 一进来就读到旧的 error 返回，m1-app 的“探针跑完、tool calling 已验证”必定失败，
   m0-smoke 也会撞上。改法照审查的建议：点 Test connection 之前记下 `since = Date.now()`，`probeState(profile, since)` 把
   `probedAt` 为 null 或早于 `since` 的档案算作 verifying（`probedAt` 是后台进程存档案时的 `Date.now()`，同一台机器的钟）；
   `readProbe(page, ref, since)`、`waitProbes(since, timeout, ref)` 跟着带上；`firstRun()` 自己取 `since`，m0-smoke 的
   `saveAndTest` 返回它，m1-app 的 `firstRunPassed` 在点之前取；`md-firstrun-helpers.mjs` 的 `waitProbe` 改为
   `waitProbe(page, ref, { since, want, timeout })`，md-app-firstrun 里四处等探针的地方都带上这次的 `since`；
   `v1-real-helpers.mjs` 的 `firstRunDeepSeek` 读档案时也带上它已有的 `since`。限制：`since` 之后那次 Test connection 必须真的
   保存了（保存会强制重新探测勾选的模型）；没有改动、不保存的测试之后用它等，会等到超时并报 verifying，是明显的失败，不会悄悄通过。
2. `changesName` 改名保存之后的等待改用 `since`，真的等到这次重新探测结束，后面 `changesFailedKey`、`changesKeptKey` 不再和探针重叠。
3. “只显示一次”的检查原来在会话开着时查，而 Open a folder 提示只在中栏没有会话时才有，那一行清没清都查不出来：
   md-app-firstrun 改为新的 `listedShownOnce`，把 listed 的会话归档（会话行菜单的 Archive，照 Claude 桌面版不确认），
   中栏回到 Open a folder 提示后查那一行不在；v1-models-app-settings 里同样查不出东西的那条删掉（MP-33 的条目不含
   “只显示一次”，状态表的这一行由 md-app-firstrun 查）。`listedHandOver` 改查档案的 `status === 'probing'`
   （`readProbe` 另返回 status；没有档案时 probeState 也是 verifying，分不出“在探测”和“没开始”）。
4. `v1-models-app-settings.mjs` 超过 2000 行（2015）：删掉自己的 `probeStates`、`folderPrompt`，改用 `md-firstrun-helpers.mjs`
   的 `waitProbe`、`readMain`（读的东西相同，`readMain` 还多了侧栏），现在 1991 行。
5. 审查没提的同类问题：`v1-models-app-settings.mjs` 的 `prepareV0`（MP-08 迁移一步的准备）还按改之前的参数调用
   `probeStates(page, final)`，ref 位置是数组、final 为 undefined，一调用就抛错、整步失败；改为 `waitProbe(page, 'fake/fake-coder')`。
6. `m6-helpers.mjs` 一行注释 132 字符，折成两行；`changesFirstSave` 上面多留的旧的一行注释删掉；本记录的冲突编号改成

### 集成时发现并改掉的（测试的问题，不是 App 的问题；1cd5a83）

1. changes 的 A20 检查“用 key B 保存失败后，框空着、没有改动再测：不保存、测试带着存着的 key A 到端点”失败：
   `tests: []`、结果 “Connection failed: Connection error.”。原因：`fake-coder-404` 的第一次测试得到 404，模型池按
   §8.3 给这个模型记下 not_found（`modelFailure.ts` 的 404 → not_found，记录在模型上、不会自己恢复，只在这个模型的配置
   或地址改变时清掉）；之后没改配置的 Test connection 在模型池里就被挡住，请求没发出，openai SDK 把这报成 “Connection
   error.”。用 404 的失败模型，A20 的“没改动、不保存、测试到端点”永远查不到。改法：合成端点加 `-400` 后缀（只对不是
   探针的请求回 400；400 按 §5.4 是 request，模型池不留记录），`selfcheck.mjs` 补两条；md-app-firstrun 的 `FAILING`
   改为 `fake-coder-400`，检查文字里的 404 改 400。v1-models-app-settings 的 Public 一步只测一次失败再换模型，仍用
   `fake-coder-404`，不受影响。
2. rejected 的“探针出错之后新会话按 no_candidate 拒绝启动、卡上 Verify now”失败：会话没有被拒绝。原因：列表门只拒绝
   探针第 1 步（ready），第 3、4 步照样通过，档案的 status 是 error，但 tool calling 是 verified，选择器不挡这个模型
   （`probes.ts` 的 `runAutoProbes` 第 1 步出错不停，`toolCallingOf` 只看第 3、4 步）。first-run.md “打开文件夹之后”的
   “探针出错”指 tool calling 因出错没有验证的情形，所以改列表门：`probeFail` 时第 1 步与第 3 步（weather 提示）的请求
   都回 400，tool calling 因此是 unverified；`rejectedRetry` 的检查文字随它改。
3. 观察（没改，留给负责人或后续的包）：首次启动里测试得到 404 之后，什么也不改再点 Test connection，结果是
