## 改了什么

**给模型看的（model-facing）**

- 附录 A（`kernel/boardText.ts` 的 `SHARED_SEGMENT`、`SEGMENTS`）：
  - 三段第一句里的 `team mode` 改为 `task mode`（立项段、合并会话的立项段、协作模式的对话段），关闭模式的对话段 `/team` 改为 `/task`；
    合成端点的 `SEGMENT_SENTENCES` 同改（`tests/fake-endpoint/scripts.mjs`）。
  - 共用段第 2、3 行（M26）：只有对话里的 Agent 和你说话，别的 Agent 都在你看不到的后台会话；你只看得到它的回复和进展摘要，看不到别的会话、
    留给 task 的消息和 `board_read`，也从不调工具。
  - 协作模式的对话段、合并会话的立项段：“Tools are yours, not the user's: never ask the user to call a tool or to open a session or the board;
    read it yourself (board_read, read_session) and put what the user needs in your reply.”；汇报一句改为需求关闭时你要的清单、报告、计划
    要从 task 读出来（`read_session` 给出 task 的最后一段回复）完整放进回复。
  - 立项段、合并会话的立项段：task 的结果交回对话 Agent，不交给你；task 可以汇总别的 task，但交给你的是对话 Agent；只有你要求时才让 task 写文件。
    合并会话的立项段里“answer directly (reply_via_dialog marks …)”改为“answer directly in your reply”。
  - task 实例段：你看不到这条会话，对话里的 Agent 用 `read_session` 读它的工作再告诉你；完整结果写在交接前或交接时的回复里（或 task 要求的文件），
    结论很短、写明完整结果在哪；不用 `agent_message` 交付结果（留给 task 的消息是给做它的 Agent 的笔记）。
  - 结案段：结果合起来满足验收才按完成关闭，缺的找立项再建 task，不带着保留意见关闭；`request_close` 的结论就是告诉你的话，写明找到或改了什么、
    完整结果在哪；你看不到结案的回复。
- 工作卡：`Team mode: …` 改为 `Task mode: …`；新的关闭模式卡片（`CardKind 'off'`，§8.3）：TaskBoard 上有需求、模式为 `off` 时用户会话每次请求都带
  `Task mode: off`、“You do the work yourself with your own tools; requests and tasks can't be created until the user turns task mode on.”、
  最近 5 个需求（更早的写成一行 `N earlier requests: board_read {}`）。
- `board_read` 第一行：`Task mode on` / `Task mode on until done` / `Task mode off`。
- 需求关闭的投递（§8.5）最后加一句：你要清单、报告、计划时从 task 读出来完整给你，从不让你调工具。
- 工具说明（`kernel/boardTools.ts`）：`agent_message` 的对话版写 `In task mode: …`，协作模式的说明末尾加 `The user never sees these messages.`；
  合并会话里 `reply_via_dialog` 的说明改为 `No collaboration needed: you answer the user directly in your reply.`（工具保留，M26 第二问的推荐）；
  `read_session` 错误第二行的例子改为 `"role":"<role>"`。
- 拒绝原文：`There are no tasks when task mode is off.`（`boardRoute.ts`），`Task mode is on: the dialog agent only relays; the work is done in tasks.`
  （`team.ts` 的 `RELAY_ONLY`）。
- 工具：关闭模式下 TaskBoard 上有需求时，对话另外启用 `board_read`、`read_session`（`team.ts` 的 `applyDialogTools`）；这时也注册用户会话的
  TaskBoard 工具（打开会话时就注册，所以重启后关闭模式的会话同样有）。基座（与没写 `tools` 的角色）的读取类总有 `ls`（`roles.ts` 的
  `readClassTools`）：只读的 task、立项、结案、临时提问、订阅、Task mode 下的对话都能列目录。
- `read_session` 省略 `role`：只有读的一方正是这个 task 上同一角色的实例时才要求写明（`teamTools.ts` 的 `defaultReadRole`）。
- 这些段合起来每个会话多约 55–220 token：合并会话的 `mori_team` 段约 650 token（原来约 430）。

## 按推荐替负责人定的

详见 [team-checks.md](../team-checks.md) 第 57–68 条，这里列要点：

1. 命令 `/task`，没有 `/team` 的别名；给模型的文字一律 task mode（M21 两问的推荐）。
2. 模式提示照 Claude 的 `Fast mode on` / `Fast mode off`：`Task mode on`、`Task mode on until done`（与 WP-09 那一行的 “Until done” 同一说法）、
   `Task mode off`；每次改变一行、不合并。
3. 关掉之后保留两个只读工具的条件是“这个会话的 TaskBoard 上有需求”（不论开着还是已关闭），不是“进过 Task mode”：只打开又关掉、没登记过需求的会话
   与 v0 完全相同（TB-03 不变）。
4. “模式关了”写进关闭模式的工作卡，不写进 `mori_team` 段（§8.5 与第 27 条不变）；卡片列最近 5 个需求（临时默认值）。
5. 只读助手总有 `ls`，只对基座和没写 `tools` 的角色；写了 `tools` 的角色照它写的；`grep`、`find` 交给 WP-08。
6. `read_session` 的“自己”按会话认（这个 task 上同一角色的实例），不按角色名。
7. `<evidence>` 用任何分隔符，分出来的词照旧不合格；给模型的说明不改（仍是“每行一项”）。
8. 进展摘要只在没有角色文件时省略角色名；有角色文件时基座仍写 `Mori`。
9. M26 的边界一句一句写进附录 A（见上），每段第一句不变（除 team → task）；`reply_via_dialog` 保留，合并会话的段里不再提它。
10. 结案段要求“结果合起来满足验收才按完成关闭”，不满足时找立项再建 task。
11. 身份段（记忆规格附录 A.1）不在这包改；subagent 会话加自己的 subagent 段，这包没有加。
12. `tb-app-flow.mjs` 的套件整体检查在 `--only` 时不做（只限那两条，端点“没有多出来的请求”照常检查）。
