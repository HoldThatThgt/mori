# 安装包带 grep、find 的程序；开关开着时写 “Available in new sessions”：检查记录（2026-10-29，U76、U77）

依据：负责人 2026-10-28/29 的两句话与选的选项（[../walkthrough-1026-checks.md](../walkthrough-1026-checks.md) 的 U76、U77）：

- U76：“we should include grep and find in offline installer”，选 “Commit pinned binaries”。
- U77：“once enabled, the title should be grey out rather shown: available on new sessions”，选 “Grey 'Available in new sessions'”。
  同一条里还有 lead 查到的一处规格没做到：重新打开的会话里 `bash`、`powershell` 不按开关换。

状态表见 [../../v0/screens/tools.md](../../v0/screens/tools.md)“内置工具”。

## 诊断

- U76：Mori 让 pi 离线运行（`PI_OFFLINE`），pi 的 `grep`、`find` 先找 `<agentDir>\bin`、再按 PATH 起 `rg --version` / `fd --version`
  （pi `utils/tools-manager.js` `getToolPath`），找不到也不下载。这台电脑上没有（`where rg fd fdfind` 都找不到），所以：
  Built-in tools 那两行一直写 “Needs rg.exe …”；打开开关后调用失败（工具卡写 pi 的 “… is not available and could not be downloaded”）；
  只读会话按 U71 的 “grep/find only if installed” 也没有 `grep`、`find`。
- U77：工具页每一行的状态只看这个会话（`tool.active`），开关是新会话的默认，所以刚打开的工具仍是 “Not enabled”。
- U77 的缺陷：pi 1.3.0 给 `customTools` 的来源是 `createSyntheticSourceInfo("<sdk:名字>", { source: "sdk" })`（`agent-session.js`
  `_refreshToolRegistry`），Mori 经 `customTools` 换掉了 `bash`、`powershell`（`workspace.ts` `shellTools`）。`refreshTools` 只把
  `builtin:` 开头的当内置工具：`bash` 算作“别的工具，照恢复的留着”，`powershell` 不在可选的内置工具里。用真的 pi 会话核对过：
  `defaultTools` 为 `["-bash", "+powershell"]` 时原来的规则得到 `null`（不重设，`bash` 留着、`powershell` 不加），修好后是
  `["read", "edit", "write", "powershell"]`。工具页的来源（`resources.ts` `toolSource`）早就把 `source === 'sdk'` 算作内置，两处规则不一样。

## 与 U56

U56 定的是：重新打开时先查 pi 恢复出的工具里有没有现在的默认工具里的 `bash`、`edit`、`write`，缺了就拒绝打开
（`This session was saved by an older version of Mori and can’t be opened.`），再按开关换内置工具（`restoredTools`：先 `refuseRestoredTools`，
后 `refreshTools`）。这次没有改这一段，拒绝的检查在 `refreshTools` 之前，输入也没变，所以 U56 本身的结果不变（`reopen` 里关掉 `bash` 之后重新打开
照常打开：现在的默认工具里只剩 `edit`、`write` 要查）。

查到的相互影响（读代码得出，没有用测试走过），两条路：

1. 开关：修好之后，关掉 `bash` 时重新打开的会话会去掉 `bash`；这个会话再运行一次，pi 就把不带 `bash` 的工具记进会话记录（每次请求前写一条
   带 `toolsAdded` 的 system 消息）。之后再打开 `bash` 并重启（或从会话文件重新打开），U56 的检查看到现在的默认工具里有 `bash`、恢复出的没有，
   就拒绝打开这个会话。`edit`、`write` 的开关在修之前就是这样（它们的来源是 `builtin:`）；关着 `bash` 时新建、运行过的会话在修之前也是这样。
2. 不碰开关（审查后补）：一次启动没找到 Git Bash 时，`shell.ts` `applyShell` 把 `NO_BASH_TOOLS`（`-bash`、`+powershell`）放进每份 pi 设置的内存里，
   `restoredTools` → `refreshTools` 读的 `settings.getDefaultTools()` 就不含 `bash`、含 `powershell`。修好之后，这次启动里重新打开的每个会话都去掉
   `bash`、加上 `powershell`（`defaultTools.test.mjs` 的第二条 U77 单元测试就是这个输入，得到 `["read", "edit", "write", "powershell"]`；修之前
   `bash`（来源 `sdk`）照恢复的留着）。这个会话运行过之后，下一次找到 Git Bash 的启动（例如重装、升级 Git for Windows，或 PATH、注册表变了）
   默认工具里又有 `bash`，U56 就永远拒绝打开它。这也与 U77 自己的说法冲突：那时 `bash` 一行写 “Available in new sessions”，可是重新打开
   （tools.md 把重新打开算作新会话）这个会话被拒绝。这次启动里新建、运行过的会话在修之前也是这样。

U56 分不出“旧版本收窄过”和“打开时没有 `bash`”（开关关着，或这次启动没有 Git Bash）。要不要改由负责人定（例如只在会话记录里的工具与现在的
默认工具、加上 `NO_BASH_TOOLS` 之后的默认工具都对不上时才拒绝），这次不改；两条路都写进了 walkthrough-1026-checks.md U77 那一行要问负责人的。
