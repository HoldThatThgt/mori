### “(default)”（M6）

原来“(not reported)”只说明服务没报告、数字是配置的值，你用 Edit 改了也照标，看不出这个数是 Mori 猜的。现在：服务没报告这一项、
而且值仍等于 Mori 的默认值（窗口 128000；Max output 为 16384 与窗口一半中较小的）时，数字后面写“(default)”，悬停
“The server didn’t report this, so Mori used a default. Use Edit to set the real value.”；改成别的值就不标、改回又标。
Ollama 只有训练窗口的模型，窗口是训练窗口、不是默认值，不再标。Fetch models 的清单同一条规则，写“Default”，悬停
“… Change it if you know the real value.”。标识 `default-value` 取代 `not-reported`。“(default)”“Default”
“Verify again”“Verifying…”都是 Claude 桌面版界面里已有的词（`ion-dist/i18n/en-US.json`）。

### 测试连接总是发出（WP-01 的观察；规格 §8.3 的 2026-10-26 补，MP-41）

根因：测试连接不带 key 时经模型池按“可用”判断（§8.2）。一次 404 让模型记下 `not_found`（只在配置改变时清除），401 让唯一的
key 记下 `auth`；之后什么都不改再测，模型池按记录直接让 fetch 失败、不发请求，openai SDK 报成“Connection error.”。
在 Node 里用真实的模型层、pi 运行时和合成端点重放首次启动（scratchpad `wp02/firstrun-timing.ts`）照出了 401 的这一种：
改之前第二次测试 2 ms 返回“Connection error.”、合成端点没收到请求。

改法（`kernel/modelPool.ts`、`kernel/config.ts`）：`createFetch` 加选项 `ignoreRecords`，测试连接带上它：发出前不看任何不可用
记录（提供商的 `connection`、模型的 `not_found`、`timeout`、`held`、key 的记录）；不指定 key 时按顺序用第一个没有记录的 key，
全部有记录时用第一个；401、429 后照原来只换到没有记录的 key。失败照常写记录（会话照旧按记录挑模型）。成功时除了用到的 key 的
记录，还清除提供商的 `connection` 和这个模型的 `not_found`（新方法 `clearAfterTest`）：测试刚证明它们不成立，否则 404 修好后
测试通过、进了主窗口，会话仍因为 `not_found` 被拒绝启动。`timeout`、`held` 不清（§5.7 等的是旧请求停下）。
改之后同一段重放：第二次测试 6 ms，发出请求，结果仍是 401 的原文。单元测试 MP-41 七条（`tests/unit/modelPool.test.mjs`）。

### m0-smoke 首次启动两步各等约 30 秒

不是模型池：`connectionCooldownMs` 与不可用记录都没有参与（Node 重放里首次启动每一步的后台进程耗时都在 0.2 秒以内：
拉取约 50 ms，保存约 40 ms，测试 130–220 ms）。是测试自己：`saveAndTest` 点 Test connection 之前用
`form.getByTestId('form-message').innerText().catch(() => null)` 读“之前的结果”，表单下方这时多半还没有结果，Playwright 的
`innerText` 会等元素出现，等满默认的 30 秒才抛错、被 catch 成 null。错的 key 那一步和对的 key 那一步各白等一次。
`page.mjs` 的 `firstRun`（大多数 App 套件的首次启动经它）和 `v1-models-app-settings.mjs` 的 `testConnection`
（`textContent`）也是同样的写法，每次首次启动白等 30 秒。改法：`page.mjs` 新加 `textNow(locator)`（元素不在就返回 null，不等），
三处都改用它。集成阶段量出：m0-smoke 整条从约 102 秒降到 46–47 秒，多出的“不改再测”一项 78 ms；快速集自己报 86–90 秒
（连构建 104–111 秒，原来约 104 秒、连构建约 129 秒），现在由回放那条线（tb 33–36 s、mem 26 s、m1 28 s）决定。

## 评审修正（2026-10-26）

评审提了一条主要、三条次要，都照改，没有不同意的。

- **主要：状态行的“Verify again”没有确定的界面用例。** 它取代了行上的 Verify，是 tool calling 没验证通过的模型在界面上
  唯一的重新验证入口，原来只有 m0-smoke、m1-app 在探针碰巧出错时才点它。现在：
  - `v1-models-app-session.mjs` 场景 `probes` 在 `rows` 之后加一步 `verify again`（`verifyAgainStep`）：
    `pv/fake-coder-notools` 判定失败的状态行带“Verify again”（只有一个，文字相同）；点它之后用 MutationObserver 记下
    行的样子，行变为 `reverifying`、状态行“Verifying…”不带按钮，合成端点收到这个模型新的探针请求，结束后回到 `failed`、
