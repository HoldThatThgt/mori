# Mori App v0 方案

状态：草案。已确认使用环境、任务记录、demo 交互去留和实现者四项，其余见第 11 节。更新日期：2026-10-19。

本文重新审视 Mori，给出"真正能用的桌面 App"第一轮方案。
依据包括：现有 `demo/` 代码审计、六份 proposal 梳理、DSH 现状调研、候选内核与桌面壳对比、pi 内核源码核查。
另有三份独立方案和三位评审的打分与合并。外部事实的核查时间均为 2026-10-19。

## 0. 结论

- **做什么**：Windows 桌面 App。打开文件夹就开始对话，批准前先看 diff，改完可以撤销，状态如实显示。
  对 App 本身不满意时按 F8 记下来，作为下一轮开发的工作单。
- **怎么做**：Electron + React/TS 作外壳，内核用 **pi-coding-agent SDK**（锁 1.3.0），跑在独立的 utilityProcess 里。
  不 fork DSH，也不自写 agent 循环。UI 只认 Mori 自己约 15 个事件的协议，以后换 DSH 或别的内核只需重写一个 driver。
- **从 demo 带走什么**：布局、视觉、`resize.js`、选区"问 Mori/反馈"、会话右键菜单、设置页的"列表→详情→编辑"模式。
  demo 的 JS 逻辑不沿用，因为它是故事板，不是应用骨架。
- **demo 里保留下来、做成真实功能的**：左右分屏、拖会话引用、工具页（Skill / MCP / Plugin）、工作回顾页。
  它们排在编码信任环之后，每一项都要有真实数据来源，不放示例。
- **先不做什么**：多 agent、监督、模型判决式验收、模型池色点、内嵌浏览器、任务记录。
  任务记录（程序持有的目标与完成检查）暂缓，等 v0 日用一段时间后再议。
- **怎么避免再"只是能跑"**：第一天就接真实模型；只按"用户旅程 + 反例"验收；
  产品代码里不许出现示例数据；每个工作单都要附 live 运行记录。

## 1. 诊断：上一轮为什么"只是能跑"

不只是 GLM 能力不够，任务本身的形状就注定只能做出浅层结果。

1. **demo 是故事板，不是应用**。
   - 每次操作都用 `innerHTML` 重绘整页（`demo/app.js:129`）。
   - 助手消息是写死的 HTML 模板，没有消息模型、流式、工具调用和持久化。
   - JS 里"演示/示例"出现约 90 次。任务阶段是全局变量，所有会话共用一份。
   - 真正经过打磨的只有布局、拖拽调宽、选区引用和拖会话这几个交互。
2. **proposal 在要求假实现**。
   - 原文："界面 demo 的启停、连接与版本均为本页示例状态"（proposal.md:240），
     "示例不读写真实用户配置"（:268）。要假的，就得到假的。
3. **规格指向仓库里不存在的 DSH 内部模块**。
   - inbox flush、`PreparedLlmCall`、`llm-retry` 等都不在本仓库，实现者只能在 mock 上画 UI。
4. **规则多是否定式**。
   - "不能/不等于/不把"在 mock 上永远成立，因为什么都没发生。
   - 验收表大多是故障注入式的基础设施测试，没有可走查的用户体验标准。
5. **核心对象"任务"从未定义**。
   - 没写谁创建任务、何时创建、完成条件由谁写。右侧"任务与文件"因此只能做成装饰。
6. **必需职责与"程序不得自行创建 agent"冲突**。
   - 单 agent 时任务会永远处于等待。
   - 默认值也被禁止（proposal.md:547），实现者只能留 mock。

所以本轮要改的不只是技术栈，还有**工作的形状**：真实内核、正向的"必须看到"、旅程验收、禁止示例数据。

## 2. 重新定位

**Mori v0：给自部署模型用的 Windows 编码 harness。**

1. **第一天就是真的**：真内核、真模型、真文件，产品里没有示例数据。
2. **状态词由事件产生**：没有对应信号的状态不显示，不说"思考中"这类无法核实的话。
3. **默认先问，可以撤销**：读取放行；写入和命令先批准，批准时就能看到 diff。
   "已停止"不等于"已撤销"，命令造成的副作用也不在撤销范围内，界面上明说。
4. **界面不谈自己**：不出现"演示""执行者""角色会话""任务版本"这类内部术语。
   正文字号不小于 13px，所有操作都能用键盘完成。
5. **慢而怪的端点是一等场景**：模型体检、请求阶段、原始请求轨迹，都为自部署模型服务。

## 3. 内核与外壳选择

| 候选 | 能给 UI 的东西 | 关键问题 | 结论 |
| --- | --- | --- | --- |
| **pi-coding-agent SDK**（MIT，1.3.0） | 文本、思考和工具参数的增量流；排队、插话与停止；会话树；编辑 diff；Windows shell | 没有内置批准，需要 Mori 用 `tool_call` 扩展自己做；周更，必须锁版本 | **采用** |
| DSH（`dsh --profile acp`） | 会话、取消、权限请求、模型切换 | ACP 只发整条消息，**没有逐字流式**；恢复会话不回放历史；开发者预览，8 天 990 个提交 | 不作 v0 内核，保留为远期 driver |
| DSH fork 改 UI | 完整功能 | 约 500 个包，结构性简化要改大量 slot，上游每天上百提交，rebase 成本极高 | 不做 |
| 自写最小循环 | 完全可控 | 最难的是各家端点的兼容怪癖，pi-ai 已经处理好 | 不做 |
| LangGraph / deepagents | 适合以后做多 agent | 对编码 UI 来说粒度太粗；OpenAI 兼容端点和 Windows 下的表现未验证 | 远期编排层候选 |
| opencode | 功能最全 | v1→v2 接口正在重做；Windows 推荐用 WSL | 不选 |
| Codex app-server | 协议设计好 | 只支持 Responses API，内网 chat-completions 端点用不了 | 只参考协议 |

pi 和 DSH 的关系：DSH 自己的模型连接器 `dsh-llm-pi-ai` 依赖 pi-ai。
因此 v0 写好的模型配置和 compat 经验，以后可以带到 DSH。

外壳选 **Electron 44.9**（自带 Node 24.22，满足 pi 要求的 ≥22.19）+ electron-vite + electron-builder NSIS，不签名。
DSH 和 opencode 的桌面版都用 Electron。Tauri 只能把 Node 内核做成 sidecar，还要多引入 Rust，对个人 App 不划算。

前端用 **React 19 + TypeScript + zustand**，一个 `applyEvent` reducer 同时处理实时事件和回放。
- 增量文本每帧合并一次，避免高频重渲染。
- Markdown 用 streamdown，代码高亮用 shiki，diff 用 @pierre/diffs，长列表用 virtua。
- 这些依赖都要在 M0 确认能离线打包，不能运行时从 CDN 拉取。

## 5. 主窗口与关键交互

**布局**沿用 demo 的三栏视觉和 `resize.js`，CSS 先抽成约 30 个 token。

- **左栏**
  - "新会话"作主按钮，Ctrl+N。
  - 导航：工具、工作回顾（沿用 demo 的位置）。
  - 项目→会话树，状态点配文字：生成中 / 等你批准 / 排队中 / 出错 / 有新结果。右键改名、归档。
  - 底部是设置和 F8。
- **中栏**
  - 顶栏：模型芯片（带体检徽章）、权限档、上下文用量。
  - 下方依次是对话流、阶段行、改动条、排队区和输入框。发送和停止按钮在同一位置。
- **右栏**：有改动时才出现，用来审阅 diff 和读文件。

各交互需要覆盖的状态如下。

1. **连接模型（空状态）**
   - 首次启动只有连接表单。
   - 体检真实发请求，逐项显示 ✓/✗：连通、列模型、流式、原生工具调用、工具结果回传、流式 usage、首字延迟。
   - 每一项附原始响应。失败的项给出 pi compat 设置建议，可以一键重测。
   - 工具调用不通时直接说"此模型只能对话"。
2. **流式（加载与生成）**
   - 旧会话先渲染最近 50 条。
   - 阶段行依次显示：`等待首字 12s` → `生成中` → `运行 npm test 8s`。
   - 60 秒无输出时变黄，这个阈值标"临时默认值"。重试显示 `重试 1/3`，数据来自 pi 的 `auto_retry` 事件。
   - 流式输出不打断输入框、选区和滚动位置。
3. **工具卡**
   - 状态流转：参数生成中 → 等你批准 → 执行中 → 完成 / 失败（含退出码）/ 已拒绝。
   - 默认折叠，展开后看参数和输出。参数不合法时显示原文并加标记。
4. **等待批准**
   - 批准卡内联在对话里，侧栏同时显示"等你批准"。
   - 编辑显示拟改 diff，命令显示完整命令行。
   - 选项：允许一次 / 本会话总是允许（命令按前缀）/ 拒绝并附理由。
   - 写项目目录外的文件、危险命令，在任何权限档下都要问。
   - 复合命令（`&&` `;` `|` 和重定向）不匹配"总是允许"。
   - 等待批准时发出的插话显示"批准后送达"。
5. **停止、排队、插话**
   - Esc 停止。如果正在等批准，按拒绝处理，2 秒内回到空闲。
   - 停止后显示"已停止 · 已执行的操作不会回滚"，并提供"撤销本轮"。
   - 生成中按 Enter 排队：排队消息由 Mori 持有，可以修改、删除，模型空闲后再发。
   - 生成中按 Ctrl+Enter 插话：在当前工具调用结束后、下一次请求模型前送达。
6. **审阅与撤销**
   - 一轮结束后改动条显示 `2 个文件 +12 −3`，点开看 diff。
   - 可以还原单个文件，或撤销本轮及之后的所有改动。
   - 文件在 Mori 改动后又被人改过，撤销时提示冲突。
   - 撤销后会告诉模型哪些文件已还原。命令造成的改动不在撤销范围内，工具卡上明说。
7. **错误**
   - 401：带"去设置"按钮。
   - 429 / 5xx：显示重试次数，可以重试或换模型。
   - 内核崩溃：自动重启，显示"已重启 · 进行中的命令结果未知"，会话可以继续。
8. **两种反馈，名字和入口都分开**
   - **反馈（针对内容）**：选中聊天或文件里的文字后点"反馈"，只问"希望得到什么结果？"。
     锚点包括消息 id 或文件路径、内容哈希、范围和原文。
   - **报告界面问题（针对 App，F8）**：自动附截图、当前界面状态和最近 50 条事件，只问"哪里不对 / 你期望什么"。
     保存为 Markdown 工作单草稿，可以直接交给下一轮实现者。
9. **左右分屏与拖会话引用**
   - 把会话名拖到聊天区左侧或右侧，放下前显示落点提示，松手后左右分屏。
     两边各自有对话流、输入框、草稿、批准卡和排队区，互不串用。关闭分屏不会停止后台生成。
   - 顶栏和右栏跟随最近操作的一侧，标题旁标明当前是哪个会话。
   - 把会话名拖进输入框，生成一个引用芯片："引用 · 会话名 · 第 3–8 轮 · 约 2.1k tokens"。
     点开芯片可以预览将要发送的原文，也可以调整轮次范围。
   - 引用内容取自该会话的事件记录（用户消息、助手正文、工具调用的标题和结果摘要），
     不再像 demo 那样取页面上渲染出的文字，所以不会混进按钮文字。
   - 发送后，消息里的引用可以点回原会话的对应位置。会话改名后，引用仍然能找到原会话。
   - 端点并发：设置里为每个端点填写同时运行的轮次上限（标"临时默认值"，默认 1）。
     超过上限的会话阶段行显示"等待端点空闲 · 会话 X 正在使用"，侧栏状态为"排队中"。
10. **工具页（Skill / MCP / Plugin）**
    - 只有这一个地方管理能力。每个条目标明来源："用户级"（所有项目可用）或"本项目"。
      页顶选择项目，列表随之切换。设置页只保留模型、AGENTS.md、权限和通用选项，
      不再像 demo 那样在设置页和工具页各维护一份。
    - **内置工具**：列出内核真实注册的工具（读取、编辑、写入、命令等）及其权限规则。
    - **Skill**：扫描用户级和项目里的 `SKILL.md`，显示用途和正文；可以按项目启用或停用；
      用户自己写的可以直接编辑。
    - **MCP**：配置 stdio 服务（命令、参数、环境变量），点"连接"后显示真实状态：
      已连接 / 连接失败（附错误原文）/ 未连接，并列出它真实提供的工具。
      MCP 工具的调用与内置工具一样走批准门。配置变化后何时生效以 M5 开头的 spike 结果为准，
      界面如实标"下一轮生效"或"新会话生效"。
    - **Plugin**：v0 中一个插件就是一个目录，里面有 `skills/` 和 `mcp.json`。
      启用插件即启用其中的 Skill 和 MCP，停用时列出受影响的能力；
      重新启用后，包内 Skill 各自原来的启停选择保持不变。会执行代码的 pi 扩展不支持，这是安全边界。
11. **工作回顾页**
    - **对内容的反馈**：收件箱列出所有选区反馈。每条显示原文、你写的期望和来源，可以跳回原消息或文件位置。
      状态只有两种："待整理"和"已整理"，不会显示没有发生过的处理结果。
    - **界面问题（F8）**：列出你对 Mori 本身的报告，可以导出为工作单。
    - **手动整理**：你勾选几条反馈后点"整理成候选"，Mori 用一次模型调用提出候选规则。
      每条候选都附来源反馈，你逐条采纳、修改或丢弃。
      采纳的规则写入用户级或项目的 AGENTS.md，并注明来源；之后的请求自然会带上它。
    - 没有定时回顾、反证 agent 和自动发布。候选永远不会在你采纳之前生效。

## 6. 架构

```text
app/
  src/shared/protocol.ts     事件与命令（zod 校验，带 {v, sessionId, seq, ts}，沿用 ACP 词汇）
  src/main/                  窗口、菜单、safeStorage 存 key、utilityProcess.fork 启动内核并在崩溃后重启
  src/preload/               contextBridge 暴露 window.mori，用 MessagePort 直连内核
  src/kernel/
    drivers/pi.ts            唯一 import pi 的文件
    drivers/replay.ts        只在开发构建中存在，界面常驻"回放模式"横幅
    approvals.ts snapshots.ts probe.ts sessions.ts
    endpoints.ts             每个端点的并发上限与轮次排队
    capabilities.ts          Skill、MCP、Plugin 的发现、启停与连接
    feedback.ts              反馈、界面问题与候选规则
  src/renderer/              React；从 demo 移植 CSS token、布局、resize、选区交互
  tests/journeys/            Playwright _electron 旅程测试
  tests/fixtures/            MORI_RECORD=1 录制的真实事件；手写的标 synthetic
docs/v0/                     screens/（每屏一张状态表）、journeys.md、defaults.md、workorders/
```

**pi 的装配要点**（已对照 pi 源码核查）

- **环境与目录**
  - import pi 之前设 `PI_OFFLINE=1`、`PI_TELEMETRY=0`、`PI_CODING_AGENT_DIR`。
  - rg.exe 和 fd.exe 放进 `<agentDir>/bin`，否则 pi 会去 GitHub 下载。
  - 每处都显式传 `cwd`、`agentDir`、`sessionDir`，否则会话会写到 `~/.pi`。
- **不执行项目代码**
  - pi 默认信任项目，打开公司仓库就会执行其中的 `.pi/extensions/*.ts`。
  - 所以要用 `SettingsManager.inMemory(..., { projectTrusted: false })`，加上 Mori 自己的 ResourceLoader：
    只加载 Mori 的扩展，以及工具页里已启用的 Skill。
  - AGENTS.md 由 Mori 自己读取后注入。
- **模型与 shell**
  - 模型用 `ModelRuntime.create({ modelsPath: null })` 在内存中注册，compat 按模型设置。
  - 显式设置 `shellPath`，拒绝 System32 下的 WSL bash。没有 Git Bash 时启用 pi 的 powershell 工具。
- **打包**：pi 是纯 ESM，不能进 Vite bundle，要标为 external，随 `node_modules` 一起发布。

**批准门**

- 用 inline extension 注册 `tool_call` 处理器，闭包里 await Mori 的 IPC promise。
  不用 `ctx.ui`，它在 SDK 模式下是空实现，`confirm` 永远返回 false。
- 每个待批准请求都绑定 `ctx.signal`，一旦中止就按拒绝处理，否则停止会卡住。
- 批准后、执行前保存文件原像。pi 的 write 工具不返回 diff，要靠原像生成。
- 退路是用 `customTools` 包装工具。**不要**直接给 `session.agent.beforeToolCall` 赋值，那会关掉 pi 自身的钩子。

**事件协议**

- 事件列表：
  - `turn.started` / `turn.ended`
  - `request.phase`
  - `message.delta {channel: text | reasoning}`
  - `tool.started` / `tool.args.delta` / `tool.output.delta` / `tool.ended {diff?}`
  - `approval.requested` / `approval.resolved`
  - `files.changed`、`queue.updated`、`usage.updated`
  - `error {kind, retryable}`、`kernel.restarted`
- 从 pi 事件的映射规则：
  - `agent_settled` 是真正的空闲信号。
  - 错误由 `stopReason` 加 `errorMessage` 合成，用量取自 `message_end`。
- 契约要求：内核把整条消息作为一个 delta 发来时，界面也要显示正确。这保证以后 DSH 的 ACP driver 可用。

**持久化**

- 位置：`%APPDATA%/Mori`。
- 每个会话保存三份：pi session（模型上下文以它为准）、`events.jsonl`（界面回放以它为准）、`snapshots/`。
- 全局保存 feedback、reports、traces。
- 重启时两份记录对账，进行中的工具标为"结果未知"。

**可替换性**：唯一的接缝是 driver，不写基类，也不预留空适配器。
将来接 DSH 就新增 `acp-driver`，用同一套 live 旅程验收。

   - 交付说明要列出未验证的项。
