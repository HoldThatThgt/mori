## 开工前查的 pi 1.3.0 行为（对照源码）

完整的表在 sessions.md 和 extension-ui.md 开头，影响设计的几条：

| 事实 | 影响 |
| --- | --- |
| 新会话在 pi 记下第一条你的消息时才写成文件；`listAll()` 只列出已有文件的会话，不报错（读不了就返回空或略过） | 侧栏 = pi 的会话列表 + 本次打开、还没保存的会话；不按列表清理草稿 |
| 改名要经打开中的 `AgentSession.setSessionName`；没打开的用 `SessionManager.open(文件).appendSessionInfo`；两个写入者会让名字和会话树错乱 | 后台进程按会话是否打开选择写法；会话正在打开时不能改名、归档、删除 |
| pi 没有删除接口，也没有归档 | 归档由界面记在本机（`localStorage` 的 `mori.archived`）；删除由主进程删会话文件（只接受 `<agentDir>\sessions` 里的 `.jsonl`）；两者都先在后台进程里关闭会话 |
| `resolveProjectTrust` 传了就每次调用、只返回是否信任；判断顺序和"记住"都要接入方自己做；`trust.json` 会抛错 | 界面先用 `trust.check` 问要不要问，回答随 `session.create` / `session.open` 带过去；后台进程在回调里按同样顺序再判断，没有回答就不加载 |
| `AgentSession.dispose()` 不通知扩展；pi 自己替换会话时先停止、再发 `session_shutdown`、再释放 | Mori 关闭会话（归档、删除、退出）时照这个顺序 |
| 打开已保存的会话时 pi 按记录恢复当时启用的工具；发给模型的工具由会话记录里的系统消息（`toolsAdded`）决定 | 重新打开时、绑定扩展之前补上现在注册了的扩展工具；下一次请求前 pi 把补上的工具写进会话记录并发给模型 |
| 扩展在 SDK 下默认拿到空的界面上下文；绑定扩展时可以传入自己的；`session_start` 在绑定扩展时发出，这时界面还不认识这个会话 | 后台进程把通知、确认、选择、输入转给界面；打开过程中、停止过程中、关闭后的询问按取消回答，打开过程中的通知打开后再显示 |
| `state.streamingMessage` 是正在生成的回复，`state.pendingToolCalls` 是正在执行的工具 | 界面重新加载后点开还在后台进程里的会话时，后台进程交出这一刻的样子 |

## 与方案不同、或需要你注意的地方

1. 上面五处照 Claude 桌面版的决定。代价：打开过的会话在本次运行里一直占着内存（M6 接入 MCP 后还有每个会话的连接），没有测量。
2. **可以删除当前会话**（先关闭再删）；pi 的会话选择器拒绝删除当前会话。生成中的会话不能删（与 Claude 相同）。
3. **界面重新加载后，本次运行里信任询问的回答清空**（回答记在界面里）：还开着的会话不受影响，点开不问；新打开同一个文件夹会再问。
4. **信任询问的接法**：方案写在 `resolveProjectTrust` 回调里弹窗；实现改为界面先 `trust.check`、回答随命令带过去，后台进程在回调里再判断一次（没有回答就不加载）。这样询问不必在后台进程里挂起，后台进程退出时打开不会卡住。
5. **不看 pi 的 `defaultProjectTrust` 设置和扩展的 `project_trust` 事件**：pi 没有导出这一步；`defaultProjectTrust` 设为 always 也会与 M3 反例冲突（登记为临时默认值）。
6. **扩展的询问只转四种**（通知、确认、选择、输入）；pi 的 RPC 模式还转达的多行编辑器、状态栏、小部件、标题 v0 不做。会话打开过程中、停止过程中、关闭后的询问不出卡、按取消回答（不然打开、停止会一直等）。
7. **Shift+Tab 从输入框回到会话树要按 6 次**（依次经过顶栏的右栏开关和权限按钮、左栏分隔线、左栏底部两个按钮）。方案没有规定路径，没有另加快捷键。
8. **还没发消息的新会话重启后不在，它的草稿也不再显示**（pi 不保存没有消息的会话，与方案 5.3"重启后草稿都在"的差异）；改过名但没发消息的会话在后台进程重新载入后名字不保留。界面重新加载不影响它们（后台进程把它补进列表）。
9. **项目里最后一个会话归档或删除后，项目行一起消失**（方案"本次打开的文件夹也算项目"）。
10. **起过名字后不能清除**（清空名字保存时什么都不写）。
11. 删除确认框对还没保存的新会话说"这个会话还没有消息。"。
12. 界面重新加载后还没点开的会话同时挂着几个扩展询问时，结束一个，侧栏就当作都没有了（下一个询问到来时再标上；点开后按对话流显示，不受影响）。

## fixture（从真实会话录制）

`tests/ui/m3-record.mjs` 经界面用的进程桥对 DeepSeek 发命令，录下命令、结果和全部事件；每个场景用新的临时数据目录和一次新的启动，
每个 fixture 只录界面在一次运行里会发的命令（"重启之后"的场景先在同一数据目录里准备、关掉 Mori 重新启动后再录；"界面重新加载之后"的场景
先准备、再只重新加载页面后录）。每个场景录完先自查，不合要求的不写入。协议最后一次改动（`mori.prompt_done` / `mori.prompt_error` 带上
是否还在运行）之后 11 个场景全部重录，一次录成；录下的文件里没有 key（已扫描）。

| fixture | 内容 |
| --- | --- |
| `two-projects` | 两个文件夹各建两个会话、各发一条消息；开头空列表，最后四个会话、两个工作目录 |
| `rename` | 打开中的会话改名，pi 发 `session_info_changed` |
| `rename-unopened` | 重启之后：列表里有上次的会话；没打开就改名，重新读取列表；再点开，名字和对话都在 |
| `delete` | 关闭会话，把会话文件移出会话目录（代替主进程删除，录制不删文件），列表里没有了 |
| `archive` | 关闭会话（归档），列表里还在 |
| `trust-deny` | 带 `.pi/extensions` 的文件夹：要问；不信任打开，`project_hello` 不在工具里，问模型能用哪些工具时没有它 |
| `trust-allow` | 信任并记住：`project_hello` 在工具里，调用时出批准卡，允许后返回 hello from project |
| `trust-remembered` | 重启之后：记住了信任的文件夹，点开会话不再问，`project_hello` 可以用 |
| `background` | A 在生成时新建 B 并发短问题；B 先结束，A 后结束 |
| `reattach` | 生成中重新加载页面：列表带回 `live`，点开时回复正在流入，带回已生成的部分，之后接着流完 |
| `ext-ui` | 信任的项目扩展 `project_ask`：通知、确认、选择、输入，作答后工具完成 |

## 测试中发现并已修正的问题

1. **第一版的状态表审查**（覆盖、键盘与边界、不造后端三组）提出约 50 条，主要有：会话树没有键盘模型；偏离方案的地方没有标出；删除失败与后台进程退出时的状态缺失；
   失去焦点就保存会在 Alt+Tab、F8 时存下半个名字；按会话列表清理草稿会在 pi 读不出时误删全部草稿；信任的"问过之后才出现要信任的内容"、trust.json 读不出等情况。都已改进状态表并实现。
2. **第一版的代码审查**确认的问题已全部修正：重新打开失败后留着旧的会话标识、删除永远报"Unknown session"；勾"记住"选"不信任"后横幅说错；改名失败后点别处又去保存；
   在 F8 报告框或信任询问里点击会关掉后面的菜单；扩展命令没开始运行时后台进程一直认为"正在生成"；两个函数超过 50 行。
3. **照 Claude 改完之后的审查**（后台进程、界面状态、文档与代码三组，每条再由一组反驳核对）确认、已修正：
   - 会话打开过程中扩展的询问会卡住打开、通知丢失 → 打开过程中按取消回答，通知打开后显示；停止过程中扩展接着问会把停止卡住 → 停止过程中按取消回答；
   - 询问的超时从界面收到时算起，界面重新加载后倒数不对 → 带上后台进程提出询问的时刻；
   - 接上时没有带回排队区、执行中工具的开始时刻，不在生成时挂着的询问也没带回 → 都带回；
   - 扩展命令里的询问：阶段行不显示"等你回答"，答完后一直停在"刚发出" → 后台进程发 `mori.prompt_done`，阶段行不在生成时也显示"等你回答"；
   - 重新打开时补工具在绑定扩展之后、不看扩展的"默认不启用" → 改在绑定之前，按 pi 的三个条件判断；
   - 界面重新加载后还没发消息的会话从侧栏消失、点不回去 → 后台进程把它补进列表；
   - 界面重新加载后还没点开的会话，侧栏状态停在列表那一刻 → 随事件更新，本轮结束标"有新结果"，后台进程退出标"出错"，图标栏圆点也算它们；
   - 删除、归档后焦点按内部顺序找下一行，会落到收起的"已归档"里 → 按屏幕上的顺序；
   - 状态表、临时默认值里的几处过时说法（回收站、文件位置、RPC 范围）→ 已改。
4. **再一轮审查**（同样三组，13 条确认、6 条驳回）确认、已修正：
   - 后台进程退出时按过时的列表给打开着的会话也标了"出错"，归档、删除后这个标记会出现在已归档的行和图标栏圆点上；归档还没点开的会话后"有新结果"跟着走
     → 标记只给还没点开的会话，关闭（归档、删除）时一起去掉；
   - 归档、删除关闭会话后，列表里它还算开着：再点时不问信任、删除重试时去关一个已经没有的会话 → 关闭后不再算开着；
   - 界面重新加载后还没点开的会话：扩展命令结束（没有开始运行）后停在"生成中"、不能归档删除；名字和排序不随事件变
     → `mori.prompt_done` / `mori.prompt_error` 带上是否还在运行，侧栏据此更新；改名和消息结束也更新这一行；
   - 同一个会话文件在打开过程中再打开一次（例如打开中按了 Ctrl+R 再点它）会起第二个写入者 → 后台进程等前一次打开完再接上；打开中不能改名；
   - 接上时扩展打开过程中的通知又接到对话流末尾 → 只在真正打开那次交出；
   - 接上时模型还没开始回复，阶段行却是"生成中" → 按这一刻定："等待模型响应"或"思考中"；
   - sessions.md 里"与方案第 6 节不同"、"会话还没保存过"的说法与改过的方案和代码不符 → 已改。
5. **真实端点走查**发现：在不信任时保存、信任后重新打开的会话里，DeepSeek 先前说过"没有 project_hello"，之后两次都坚持原来的回答（列工具时没有它，第一次让它调用时它改用 bash 去查 `.pi` 文件夹）。
   核对后不是 Mori 的问题：后台进程里这个会话启用了它，下一次请求前 pi 把它写进会话记录（系统消息的 `toolsAdded`），合成端点也确认请求里有它；写明"工具已经可用、直接调用"后 DeepSeek 调用成功。
   走查里"列工具时有它"这一项记为 KNOWN（模型行为），新增两项检查 Mori 这一侧（会话启用了它、pi 声明给了模型）。
6. **M1 回放的合成长会话**用了占位的会话文件名，回放桥现在比较会话文件，改为用录制里的真实路径。
7. 打开中的会话顶栏先显示"没有可用模型"（还没有来源）→ 打开完成前不显示模型。
